# 2. Sergi's branches: expand Qibo's `Condition`

## What was built

Before Roman left Elis suggested that in order to expand the conditional operations to multiple gates, other types of inputs such as a dictionary (to track which gates apply to which qubits) could be passed to extend the capabilities of `Condition()`. Starting from this point and Roman's initial Qibo conditional-gate prototype Sergi developed `sergi-conditional-operations` and on top of that `sergi-switch-bool` with the goal of extending the set of conditional operations the prototype could accomodate.

`sergi-conditional-operations`

- Replaced the register-name argument with a link to the Qibo `MeasurementResult` or one of its measured bits: `Condition(result.symbols[0], 1, gates.X(1))`. It also supported comparing a whole measured register with an integer or bitstring.
- Modified `to_qasm3()` into a dedicated exporter that handled measurements in circuit order and could reuse classical registers.
- Added a `Qibo → OpenQASM 3 → Qiskit → Aer` example and tests.
- Added handling to keep conditions linked to measurements when circuits were copied, decomposed, or serialized.

`sergi-switch-bool`

- Changed the API to `Condition(condition, body)`. Conditions could now be Boolean expressions of measured bits `(&, |, ^, ~)` or whole-register comparisons `(==, !=)`.
- Allowed bodies containing several gates or a circuit, with nested conditions, and switch-like cases by passing a dictionary as body.
- Expanded OpenQASM 3 export: its Qiskit-compatible mode lowered complex conditions into nested if/else statements; another mode emitted OpenQASM 3 Boolean operators and switch syntax.

| Form in `sergi-switch-bool`                                       | Meaning                                  |
|:------------------------------------------------------------------|:-----------------------------------------|
| `gates.Condition(first, gates.X(3))`                              | Apply `X` when a one-bit result is true. |
| `gates.Condition(register == "10", gates.X(3))`                   | Test a whole measured register.          |
| `gates.Condition(register, {"01": gates.X(3), "10": gates.Z(3)})` | Treat a dictionary body as switch cases. |

## Why it mattered

The work proved that **Qibo could represent and export richer measurement-dependent circuits.** It also exposed an API design problem: one `Condition` operation carried both Boolean branching and switch semantics, with the body type obscurely changing the meaning of the call. That made the distinct control-flow concepts (conditions that translate to if/elif/else and switches) very hard to read in the circuit's code. Elis next phase resolved the overloading of `Condition` by completely redesigning the api to incorporate explicit control-flow syntax, closer in design to that used for QEC.

The result from this built was an enhanced Qibo-defined `Condition` operation that could handle multiple conditional scenarios and that would run through path `Qibo--> QASM3 --> Qiskit --> Qiskit Aer execution`.

**Limitations:** At this point however, the `Condition` is hard to use and there's no Qibo native execution path.

“Native” means that calling `circuit(nshots=...)` on a supported simulator makes Qibo itself read each shot’s mid-circuit result and run the selected branch. Sergi’s work up to here could represent and export more conditions, but explicitly rejected that kind of Qibo simulation. Elis implemented native execution later on `eo-switch-native-execution`, after her separate API redesign on `eo-switch-api`.
