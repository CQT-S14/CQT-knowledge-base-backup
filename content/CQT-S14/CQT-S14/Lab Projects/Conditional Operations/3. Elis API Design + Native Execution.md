# 3. Elis's: API redesign + native Qibo execution

## What was built

### 1. API redesign — `eo-switch-api`

Elis first replaced Sergi's overloaded public `Condition` with **two distinct control-flow operations**:

| Operation | Meaning |
| --- | --- |
| `gates.IfElse(condition, then_do, else_do=())` | Choose between true and false bodies; the omitted `else_do` is a no-op. |
| `gates.Switch(result).case(value, body).default(body)` | Choose a body from a measured bit or register value. |

`gates.IfChain` is a convenience builder for `if`/`elif`/`else`; it produces nested `IfElse` nodes, not a third operation. Measurement results gained explicit methods such as `is_one()`, `bit(0).is_zero()`, and `equals("10")`; `qibo.conditions` provides `all_of`, `any_of`, `xor_of`, and `not_`.

This branch also adapted Qibo's circuit bookkeeping and OpenQASM 3 exporter to the new operations. **At this point, Qibo could represent and export them, but** `circuit(nshots=...)` **still rejected native control-flow execution.**

### 2. Native execution — `eo-switch-native-execution`

Elis next added Qibo's own **shot-by-shot branch execution**: after a mid-circuit measurement, the simulator evaluates that shot's condition, applies the selected `IfElse` or `Switch` body, and continues. Commit `cd0db8ff2` implemented this for the NumPy backend; `379018232` added qibojit's CPU Numba platform. Tests cover stochastic outcomes, nested branches, repeated execution, and density matrices. Unsupported platforms fail explicitly.

The following examples show the combined API and native simulator support. The first block deliberately exercises many condition forms in one circuit rather than representing a particular algorithm.

### Syntax examples

`IfElse`**:** build conditions from measurement results

```py
from qibo import Circuit, conditions, gates, set_backend

set_backend("numpy")
circuit = Circuit(4)
circuit.add([gates.H(q) for q in range(3)])

measurement = gates.M(0, collapse=True, register_name="feedback")
m = circuit.add(measurement)
syndrome = circuit.add(gates.M(1, 2, collapse=True))

measured_one = m.is_one()                     # qubit 0 measured 1
first_bit_zero = syndrome.bit(0).is_zero()   # qubit 1 measured 0
checks = (
    measured_one,
    first_bit_zero,
    syndrome.equals("10"),                    # qubits 1, 2 measured 1, 0
    conditions.all_of(measured_one, first_bit_zero),
    conditions.any_of(measured_one, first_bit_zero),
    conditions.xor_of(measured_one, first_bit_zero),
    conditions.not_(measured_one),
)

for check in checks:
    circuit.add(gates.IfElse(check, then_do=gates.X(3)))
circuit.add(gates.M(3, register_name="result"))

print(measurement.register_name)  # "feedback"
print(circuit(nshots=1000).frequencies(binary=True))

```

Each entry in `checks` demonstrates one condition form; the loop applies them to qubit 3 as a compact syntax example, not a particular algorithm.

`Switch`**:** choose from one measured register

This circuit flips whichever measured bits were `1`, so its ideal final result is `00`. It uses the `Circuit` and `gates` imports above.

```java
switch_circuit = Circuit(2)
switch_circuit.add([gates.H(0), gates.H(1)])
bits = switch_circuit.add(gates.M(0, 1, collapse=True))
switch_circuit.add(
    gates.Switch(bits)
    .case("10", gates.X(0))
    .case("01", gates.X(1))
    .case("11", [gates.X(0), gates.X(1)])
    .default([])  # "00": do nothing
)
switch_circuit.add(gates.M(0, 1, register_name="final"))

```

### `IfChain`: write an `if`/`elif`/`else` sequence

Here the two measured bits choose one operation on qubit 2. Calling `.else_()` completes the builder and returns nested `IfElse` operations.

```java
chain_circuit = Circuit(3)
chain_circuit.add([gates.H(0), gates.H(1)])
bits = chain_circuit.add(gates.M(0, 1, collapse=True))
chain_circuit.add(
    gates.IfChain()
    .if_(bits.equals("10"), gates.X(2))
    .elif_(bits.equals("01"), gates.H(2))
    .else_([])  # "00" and "11": do nothing
)
chain_circuit.add(gates.M(2, register_name="result"))

```

Both steps are present in the fork's `develop` branch.

## Why it mattered

The redesign makes true/false decisions and multi-case choices readable as different operations. Native execution then lets Qibo simulate and test those choices locally, without an OpenQASM 3/Qiskit round trip. An explicit `.default([])` makes a no-op switch case visible.

**Limitations**:Native support is platform-specific, NumPy and qibojit Numba are supported; GPU, compiled, distributed, Clifford, and hamming-weight paths remain unsupported. This native execution is **local Qibo simulation**. Hardware execution came later via the separate [OpenQASM 3/Qiskit route](https://file+.vscode-resource.vscode-cdn.net/Users/elis/Desktop/Work/PROJECTS/Quantum/forks-CQT-S14/CQT-conditional-operations/confluence/4_hardware_demo.md); the hardware jobs do not use Qibo's native simulator but we introduced it (aside from completeness) because that gives us a direct way to test the API’s behavior and calculate expected results locally before comparing them with Aer or hardware.
